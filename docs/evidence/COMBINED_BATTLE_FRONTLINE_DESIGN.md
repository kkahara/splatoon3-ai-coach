# Combined battle frontline: feasibility and implementation design

**Status:** feasibility investigation and design, 2026-11-04; Phase 1 result is recorded in [PHASE1_INITIAL_COMPARISON.md](../../analysis/battle_frontline_phase1/PHASE1_INITIAL_COMPARISON.md). No production detector has been changed and no model has been validated. This report describes the inspected local checkout; default activation is not a deployed or accuracy claim.

## 1. Feasibility conclusion

A **paint-only experimental contour** is feasible from intact map screenshots by reapplying the current, provenance-pinned color classifier and stage polygon in an isolated research tool. It is **not** reconstructible from ordinary saved `map_observations.json`: that file retains totals and fractions but no spatial per-pixel classes. A player-augmented contour is blocked by missing gameplay-map player coordinates, reliable team association and position lifetimes. A full combined contour additionally needs mode-specific objective positions and navigable stage geometry. Existing scoreboard/control facts can provide contextual, signed evidence only after a registered objective location is available; counts do not locate the objective.

Treat the proposed output as a map-space estimate of an observed influence boundary, never a claim about player participation, safe traversability, or match outcome. Unknown evidence reduces availability or widens uncertainty. It never becomes a zero-valued opposing observation.

The map sampling path is governed by stage identity, Ready evidence, team-color calibration, confident map-open detection, and sample interval (`match_side_effects.py`). It writes sparse points only while the map is open. `map_ink.py` classifies on the source image, clips within the polygon, counts ally/opponent/other pixels, then discards the arrays. The debug JPEG path (`write_map_ink_diagnostic`) recomputes and paints a visualization only when diagnostics are requested; JPEG colors and legend overlays cannot be treated as ground-truth class labels. There is no map-ink `GameStateSnapshot` field; it is a separate sidecar rather than a fusion product.

**Source hierarchy for a research prototype:** immutable screenshot/video frame + exact stage polygon + calibration and classifier version/config + timestamp/result refs; then any reproducible class-mask derivative with its own source hash. Historical aggregate observations alone support only whole-polygon fractions. Reclassification can differ from old totals if the historical calibration/config or source frame is unavailable; record that mismatch and leave the old observation unchanged.

## 3. Player positions and mode-specific objective evidence

`PlayerCountReading` (`vision/models.py`, `vision/player_count.py`) observes X markers in eight top-HUD slot ROIs. `GameStateSnapshot.ally_alive_count` and `.opponent_alive_count` are team totals, not coordinates. The code inspected has no active map/player tracker, no screen-to-map transform for local or remote players, no persistent teammate/opponent identity, and no position-to-alive-count association. A local death can invalidate a local-player track in a future system only when that track is independently established. Do not distribute an alive count as synthetic player points.

A team-level control state can give a **signed** contextual cue only for a registered objective region with direct, fresh evidence. Neutral/unknown state contributes no signed influence. Held state ages and eventually expires for the proposed derived model; the existing fusion state remains untouched.

## 4. Spatial information lost and detection requirements

1. **Before persistence:** `classify_bgr` has ally/opponent/other masks in memory; `MapObservation` stores scalar totals and fractions. This is the primary paint-spatial loss. Optional diagnostics are rendered JPEGs, not lossless masks.
2. **Before ScenarioContext:** map samples lose their source IDs, polygon hash, denominators and calibration association. The committed inspection exporter records aggregate provenance but cannot recover discarded pixels. Objective context takes sparse score/control samples; Tower native pod boxes and Clam basket visual state do not enter the ordinary objective inspection projection.
3. **Before coaching:** `ScenarioContext.objective` is inspection-only and excluded by default serialization. The current LLM projection handles selected death-episode evidence, not spatial objective streams or map masks.
4. **Never detected:** map-coordinate player positions/team identities, paintable/walkable regions, ramps/levels, spawn/home boundaries, mode-specific objective geometry, and reliable map-to-world correspondence. The repository has no active detector output that meets these contracts.

Detection prerequisites for the **player branch**: map-overlay icon/marker candidate with map-coordinate bounding region, team-color or other explicit team association, independent alive-state association or `unknown`, confidence/ambiguity, source frame/PTS, and validated tracking/expiration across map openings. A gameplay camera detection needs an independently validated screen-to-map transform; camera pixel coordinates alone are unusable. Before assuming a marker represents a player, label negatives such as spawn icons, super-jump targets, pings, objective symbols and overlapping icons. Slots may be associated with marker tracks only after identity validation.

Detection/registration prerequisites for the **objective branch**: stage-plus-mode objective area/route/checkpoint/basket anchors in canonical map coordinates; direct observations that locate a moving objective or validated fixed anchor; explicit source/team, timestamp, observed versus held quality and uncertainty; unknown for unbound count cues. No detector thresholds or fusion rules need changing to design this evidence.

## 5. Coordinate system and stage geometry

Use normalized `(u,v)` coordinates on a **registered overlay-map image** (`u` rightward, `v` downward), plus a `stage_id`, map orientation, geometry version/hash, screenshot dimensions and transform quality. This is a candidate canonical *image-plane* coordinate system, not automatically a canonical physical/world coordinate system. Confirm that camera/map zoom, orientation, and overlay layout are stable across recordings, resolutions, teams, and modes. If not, register each screenshot with landmarks and store the transform and residual; failed registration makes the spatial estimate unavailable.

The 25 canonical `stage_mask.yaml` polygons provide an inclusion boundary and hash; they cannot prove playability inside it, walkability, height, crossings, routes or home connectivity. A viable stage profile needs separate reviewed layers: navigable ground and paintable surface masks; obstacles/water/void; connectivity graph or geodesic distance; ally/opponent spawn or home seed regions after side orientation; lane IDs and lane boundaries; mode-specific objective areas/routes; and exceptional states such as Mahi-Mahi tide. Version every layer and validate alignment against screenshots. Do not turn polygon containment into path connectivity.

Define normalized advancement `a∈[0,1]` from an ally-home geodesic coordinate toward opponent home, with lane-specific geodesic coordinates on the reviewed graph. A reverse-side recording uses its own pinned transform. When home seeds/graph are missing, report image-space contour only and leave advancement/lane metrics unavailable. A long or multiple-component contour cannot be collapsed to a single advancement without documenting which crossings were selected.

## 6. Proposed derived-evidence contract and builder

Put a **standalone, opt-in derived-evidence builder under `analysis/`** (proposed `analysis/battle_frontline.py`) because it combines saved vision observations with reviewed stage geometry but neither owns detector readings nor changes Scenario grouping. Keep research annotation/export tools under `tools/diagnostics/battle_frontline/`; a future CoachInput consumer needs separate authorization. Inputs are immutable source frames or explicit classified-mask artifacts, not `MapInkSample` fractions.

Suggested versioned models, with a Pydantic boundary for persisted data:

| Contract | Required fields and semantics |
|---|---|
| `SpatialFrameEvidence` | Source artifact/hash and frame/result IDs; video time + optional PTS; stage/mode/side; source image dimensions; registration transform/residual; polygon/geometry hashes; classifier config/calibration refs; class-mask ref/hash or `unavailable` with reason. Raw `MapObservation` values remain separate. |
| `PlayerSpatialObservation` | Point/footprint in registered map coordinates, team `ally/opponent/unknown`, identity/track key only if verified, visibility/occlusion, independently supported alive status `alive/dead/unknown`, detector/association scores, sample and establishment times, source refs, expiration bound. |
| `ObjectiveSpatialObservation` | Mode and semantic type; point/area/route ref; team/control sign `ally/opponent/neutral/unknown`; direct/held quality, observed and establishment times, source refs, positional uncertainty, expiration bound. Native score values remain separate. |
| `FrontlineEvidence` | Schema/algorithm version; source set/hash; input availability per component and omission reasons; raster/grid/transform refs; one or more labeled main/secondary contours with coordinate arrays; uncertain/contested band polygon or raster; advancement/lane intervals if registered; spatial reliability/coverage; temporal support interval; warnings and provenance to contributing samples. |

Keep probability/confidence vocabulary calibrated: classifier similarity, image-registration residual, input coverage and contour uncertainty are different quantities. An overall confidence number is optional and must be calibrated on held-out annotations before display; until then expose components and a categorical availability grade. Track signed objective evidence separately from paint and players so a control cue cannot silently rewrite the visible paint map.

## 7. Proposed algorithm and uncertainty

The algorithm below is a **hypothesis**, not implemented or empirically tuned.

1. **Observe and register.** For each map-open screenshot, validate source identity, stage/side, polygon hash, orientation, calibrated color classes and registration. Rasterize ally/opponent/other into a common grid at declared resolution. Treat unclassified pixels as unknown, not neutral territory. Stop if the source image or historical calibration cannot be verified.
2. **Paint influence.** Smooth the signed paint field on **navigable graph distances** or within validated same-surface regions, with kernels that do not cross walls/voids/levels. Weight by local color validity, occlusion and registration quality. Preserve original class grid and smoothed derivative separately. Without navigability, restrict to image-space smoothing and label it exploratory.
3. **Home-connected territory.** Flood from reviewed ally/opponent home seeds through traversable, team-supported cells. Isolated paint islands remain visible paint but are not automatically controlled territory. Unknown gaps interrupt a connection; do not bridge them with a Euclidean kernel. Record disconnected components and uncertain connectivity.
4. **Player influence.** Add compact local kernels only for independently located, team-associated, currently supported player positions. Weight by association quality, occlusion and elapsed video time; expire at a predeclared maximum age or on contradictory observed lifecycle evidence. A roster total may cap or flag impossible track multiplicity, but cannot create coordinates. An unlocated or team-unknown marker contributes no signed field.
5. **Objective relevance.** Apply mode-specific spatial relevance around a registered zone, tower route position, Rainmaker route/carrier, or baskets. Keep relevance (where boundary accuracy matters) separate from control sign (which team currently has direct fresh evidence). Turf War has no discrete objective contribution unless a separately reviewed stage feature is registered. Expired/held/unknown objective evidence contributes no signed field.
6. **Local reliability fusion.** Combine per-cell signed paint, player and objective fields only where each input has local support: `S(x)=Σ w_k(x)·s_k(x) / Σ w_k(x)` over available `k`. Record each weight, sign, support mask and omission. Global weights cannot let a single distant player overwrite observed paint everywhere. Calibrate weights by stage/mode on training cases and compare against paint-only ablation; never optimize on the held-out six if they are the only reference set.
7. **Contours and band.** Extract zero crossings and connected components on navigable cells. Prefer a main contour that separates connected ally/opponent home influence and spans supported lanes; retain other supported contours as secondary with reason. If topology is unresolved, output multiple candidate contours rather than inventing a main one. Define a contested/uncertain band where signed magnitude is small **or** source registration, classification, connectivity or modality disagreement is high. Report wide/empty regions as such.
8. **Advancement and time.** Intersect each contour with reviewed lane centerlines and report crossing intervals and normalized geodesic advancement; if multiple crossings, report all and a declared summary rule. Temporal smoothing combines only adjacent observations with verified same registration/side/geometry and a predeclared maximum gap. After a gap, reset state; do not interpolate a line through unseen play, MATCH_END, stage change or orientation change. Preserve both raw and smoothed contours and their input times.

An output may be `unavailable` (missing image/registration), `paint_only`, `paint_plus_players`, or `full_combined`. The names reflect **observed input presence**, not model superiority. A nominal full model with no qualifying player/objective points must be reported as the lower effective variant. Contradictory evidence broadens the band or makes the component unavailable; it does not get resolved by rank/order preference.

## 8. Six-image prototype, review UI and measurable validation

The six conversation screenshots are an initial **development/reference set**, not a reliable generalization test. They were matched to the recording supplied by the user, and clean source frames are now hashed under `analysis/battle_frontline_phase1/clean/`. The first image (HUD clock 0:05) is used as the Back–Center–Front orientation reference, **not** as a frontline label. The next five images (HUD clocks 3:31, 1:18, 3:58, 0:45, 2:24) retain provisional red frontline sketches. These sketches remain unconfirmed. The initial paint-only comparison and its limitations are recorded in the Phase 1 report. Six screenshots cannot establish which cue caused a line shape or which line is correct.

The clean frames came from `~/Movies/review_topdown/en_review_topdown_RJIG-LYDA-ASPU-VCHF_2026-10-24 14-09-38.mov`; source and frame hashes are in `analysis/battle_frontline_phase1/study.json`. Stage identity was read as Scorch Gorge. A manually selected transform from the existing Scorch Gorge stage polygon is provisional and has visible registration limitations. The files under `tests/fixtures/tower_control/` remain **two narrow HUD crops** (`museum_30`, `makomart_110`), unsuitable for map-frontline annotation. `analysis/development/tower_control/` contains mixed HUD development frames and was not substituted.

Proposed lightweight local visual-review tool (design only): a screenshot viewer with a pan/zoom overlay; editable human polyline(s) and uncertain band; generated main/secondary contours and their band in different colors; toggles for source-class mask, polygon, home seeds, player/objective input locations and provenance; approve/reject/adjust controls; and reason codes such as `wrong_registration`, `wrong_team_color`, `multiple_fronts`, `unobservable`, `geometry_missing`. Save annotations as versioned JSON with source image hash, normalized points, annotator/revision/time, adjudication and explicit `unannotatable` status. No CSV edits, source-image rewrites, model auto-approval, sealed policy data, or inferred player positions. A local browser review UI can follow existing diagnostic patterns such as `tools/diagnostics/map_ink_reference/annotate.html`, but the frontline tool needs its own isolated dataset and output path.

Evaluation design:

- Establish an annotation guide: what a “frontline” means when paint is disconnected, map regions are unreachable, multiple lanes disagree, or evidence is visually absent. Digitize the five red sketches as **candidate** line labels and use the first image for the back/front orientation and center reference. Have reviewers confirm or adjust them in the proposed UI; obtain independent annotations and adjudicate disagreements before tuning. Six screenshots suffice for UI/contract smoke checks and qualitative failure taxonomy, not statistical acceptance.
- Freeze source/image hashes, geometry and annotation revisions; split by **recording and stage** for development versus holdout. Collect more examples across stages, modes, map orientation, ink imbalance, map-opening cadence, overtime and ambiguous player icons. Do not select only easy map-open frames.
- Run three separately identified variants on exactly the same eligible frames: `paint_only`; `paint_plus_players` **only when validated player points exist**; `full_combined` **only when registered objective geometry and supported state exist**. Record effective variant and missing-source rate, not just intended label. Do not impute inputs to fill an ablation.
- Metrics: median and 90th-percentile symmetric contour distance in normalized map units; lane-crossing advancement absolute error; band coverage of human polyline and band area fraction; percentage of frames with valid output; incorrect main/secondary topology; stage/side registration failure; inter-annotator disagreement; and false confident output on deliberately unobservable controls. Bootstrap by recording rather than frame. Report metrics by stage/mode and effective evidence variant.
- **Proposed phase gates**, to preregister before scoring: source/hash integrity 100%; zero asserted player/objective coordinates without direct refs; every known invalid/unregistered frame returns unavailable; all annotated front segments lie in the reported uncertainty band for at least 90% of held-out annotatable frames while band area stays below a human-approved cap; added modalities improve paired contour/lane error without materially increasing false confident outputs. Set numerical distance/area caps from the annotation guide and human disagreement on a larger held-out set, not from these six screenshots. Phase one may only test annotation capture and feasibility, not claim this held-out criterion has been met.

No claim of measured improvement is possible yet. A full combined comparison is **not evaluable** until player and objective spatial inputs exist. It is acceptable for the result of phase one to be “paint-only fails” or “frontline not identifiable from map ink.”
