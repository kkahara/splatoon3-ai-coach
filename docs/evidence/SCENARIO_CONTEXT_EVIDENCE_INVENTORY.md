# ScenarioContext gameplay evidence inventory

**Inspection date:** 2026-11-03. **Scope:** the current local working tree, including existing uncommitted implementation. “Default-enabled” below means enabled by this checkout's `configs/default.yaml`; it is not verification of deployed production configuration or measured detector accuracy.

This is an implementation inventory and a proposal for further work. It does not evaluate coaching quality, change observations or consumers, run a report-quality experiment, or authorize implementation. No sealed policy key or experimental policy assignments were needed.

## Main findings

1. The system is already rich in local death/recovery, roster, map, special-gauge and Splat Zones evidence. Several downstream projections remove source identifiers, quality, sampling coverage or temporal detail.
2. Four ranked modes already have a discriminated `ScenarioContext.objective` inspection path. Tower, Rainmaker and Clam evidence is **not absent from the implementation**, but the detectors are opt-in and this context is excluded from ordinary CoachInput serialization and the LLM projection.
3. Tower's active opt-in path reads score pods and explicit control/checkpoint messages. Its marker-position helper is not called, `tower_team` is not resolved during scan, and marker/checkpoint fusion experiments are not wired into active fusion. A model field or a helper does not establish a live capability.
4. Clam basket visual state is fused, and separate basket-run/transition-bound diagnostics already exist. Basket state is not in ScenarioContext; validated scoring-team attribution is deliberately disabled. Score changes and basket closure therefore cannot currently be joined into an authorized team-specific gameplay sequence.
5. The highest-priority next slice is **preserving roster/map observation provenance and explicit coverage gaps**, before exposing more evidence to coaching or adding detection. The proposed slice appears in section 5.

## Reading the inventory

**Status:** `P` = default-enabled production path in this checkout; `X` = opt-in experimental/development path; `G` = diagnostic/helper path, not part of normal analyze-to-coaching execution; `—` = unavailable or not applicable. Status describes activation, not reliability.

**Evidence access:** raw persisted evidence, an inspection artifact, a full in-memory CoachInput, a serialized CoachInput and the authorized LLM view are distinct boundaries. Having a field in one does not grant access in the next. “Report” means the player-facing public review renderer; the developer Analysis Viewer/VMV is called out separately.

**Loss categories:** A = detected but not admitted/preserved by fusion; B = fused but absent from ScenarioContext; C = in ScenarioContext but unavailable to the current coaching projection/claims; D = available to coaching but absent from the deterministic report evidence; E = no active detection capability. Rejection of ambiguous observations is often an intentional safety boundary, not a defect to remove. Raw readings usually remain on disk, so downstream loss is often recoverable without re-decoding.

**Verified** means checked in executable code and call sites, with relevant tests inspected or run. It does not mean independent accuracy was established on unseen matches. **Hypothesis/validation required** identifies a possible consequence or proposed extension that this inventory has not empirically demonstrated.

### 2.3 Team roster and alive counts — P, all modes

1. `PlayerCountDetector` measures masked dark X markers in eight HUD slot ROIs and retains per-slot distances, edge energies and visibility. A missing icon edge invalidates roster visibility; it does not produce “all alive.” It does not identify weapons, names or connection status.
2. Fusion converts X-marker counts to ally/opponent alive counts and debounces each side. The first usable count is accepted; changed counts need consecutive agreement. During a pending change the previous accepted count can be held briefly. An unreadable result clears pending confirmation; an unscheduled/no-result frame supplies no counts and leaves debounce memory alone. Snapshot provenance is aggregated, without an explicit per-side roster observed/held quality or per-side observation age.
3. `observations_from_snapshots` requires both counts and retains confidence and snapshot evidence IDs. `build_players_evidence` compresses consecutive equal count pairs to their **first** sample and projects into `PlayerCountPoint`, keeping only time, counts and reliability. Confidence and source IDs are lost there. The compressor does not encode missing-frame gaps or the final confirmation of an unchanged run.
4. Context anchor/death lookups use nearest absolute time within a bound; a point may be after the death. Coaching's `pre_death_roster` deliberately uses the last trajectory point at/before death minus its offset. That selector does not apply a separate freshness maximum to the compressed point. Plausibility tagging marks intervals around unexplained fast count increases and suppresses unreliable anchor/pre-death evidence; it does not fix underlying readings.
5. CoachInput also has a separate PlayerCountClock-derived labeled sample/window/context path. The LLM receives selected pre-/at-death counts, window points, reliability and summary fields, not the full original trajectory. The report renders an admitted roster observation or an anchor fallback and suppresses exact-sample duplication with roster factors.

The current defaults keep `roster_evidence=true` but `roster_scoring=false`; evidence capability and ranking activation are separate. [Detector](../../src/splatoon3_ai_coach/vision/player_count.py), [fusion/debounce](../../src/splatoon3_ai_coach/vision/state.py), [shared series/compression](../../src/splatoon3_ai_coach/analysis/player_count_series.py), [context projection](../../src/splatoon3_ai_coach/analysis/scenario_evidence.py), [pre-death selector](../../src/splatoon3_ai_coach/coach/death_importance.py), [window context](../../src/splatoon3_ai_coach/coach/player_count_context.py), [report](../../tools/public_site/results.py).

### 2.4 Map opening, map ink and team-color identity — P with gates

MapOverlayDetector reports visibility independently of lifecycle. Fusion/events preserve MAP_OVERLAY intervals; ScenarioContext records counts, relevant event IDs, earlier overlay timing and recovery associations. Absence becomes `not_observed` only when source observability, match respawn-map coverage and the episode's observation coverage permit it; otherwise it is unknown with a reason. “Before death” has unbounded earlier-event lookup, not a fixed recent-check window. Map ink never sets these map-check fields.

Map ink bypasses state fusion deliberately: the scan samples the map only under Ready/color/stage/polygon/map-open gates and persists `map_observations.json`. Its richer records contain stage/mode, pixel totals, three fractions, region diagnostics, overlay evidence IDs, sampling-mask source and polygon hash. Match identity/calibration sidecars retain match-level color evidence. `MapInkSample` carries only time and the three fractions into ScenarioContext; geometry identity, denominator counts, evidence IDs and calibration linkage do not survive this projection.

Coaching selects one nearest admitted in-window ink sample, preferring a pre-anchor sample on an equal-distance tie. That sample may legitimately be post-death, and its temporal relationship is explicit. All in-window samples remain in context, but the LLM/report do not expose the trajectory or comparable before/after ink changes. The report shows whole-number **shares of detected ink**; that is not total map ownership, a control assertion or the final Turf War result. ### 2.6 Splat Zones scores, penalties, control and progress — P

ScoreDetector reads screen-left/right primary digits and optional `+N` penalty pills. Fusion mode-gates Splat Zones, maps left to ally/right to opponent, tracks observed/held/rejected/unknown quality, applies trajectory plausibility and offline contradiction retractions, and holds visible penalties separately. `not_shown` is not a measured zero.

`ScenarioContext.score` contains anchor/pre-death/lookback samples, not a full score series. It copies only observed values while retaining quality and filtered score IDs; held or rejected values become null. Its lookup prefers a sample with both primary counts observed within the bounded target window, otherwise a sample with any score/penalty observation.

ZoneControlDetector independently classifies scoreboard pod highlights. Fusion confirms/briefly holds neutral/ally/opponent control; unknown breaks the transition chain. Context has state/quality/IDs, sparse samples and confirmed transitions, and coaching derives only observed control/pattern facts. Counter decreases do not establish zone control. The legacy zone anchor sampler can select a prior nonunknown sample within its gap even when a more recent snapshot is unknown; this differs from the new objective sampler's latest-snapshot policy.

The Splat Zones objective-progress adapter keeps fresh per-team primary counts and compares bounded endpoints: a positive `previous−current` amount is progress; **zero or a negative amount is labeled no_progress**. Long gaps remain unknown. This differs from the Rainmaker/Clam adapters, which make increases unknown, and should be reviewed before treating the shared schema as having identical mode semantics. Penalty consumption is not progress in this adapter. Context pairs each objective observation with same-snapshot roster/lifecycle data. Coaching derives three optional temporal claims: roster advantage with no observed progress, sole ally alive during progress, and observed post-death progress followed by bounded no-progress observations. These consume the **legacy Splat Zones `objective_progress`**, not `objective.progress` for other modes.

The active `match_scoring._build_input` call explicitly enables score and zone-control facts, although the lower-level builder defaults both options off. The LLM receives score/penalty arithmetic and selected control/temporal facts; explicit score claims exist, but there is no dedicated zone-control claim-definition family. The deterministic public evidence list displays active score/count factors, not the complete penalty/control/progress series or all temporal claims. [Score reader](../../src/splatoon3_ai_coach/vision/score.py), [score fusion](../../src/splatoon3_ai_coach/vision/score_fusion.py), [score context](../../src/splatoon3_ai_coach/analysis/score_context.py), [control fusion](../../src/splatoon3_ai_coach/vision/zone_control_fusion.py), [control context](../../src/splatoon3_ai_coach/analysis/zone_control_context.py), [progress adapter](../../src/splatoon3_ai_coach/analysis/splat_zones_objective_progress.py), [temporal derivation](../../src/splatoon3_ai_coach/coach/objective_temporal_facts.py), [score arithmetic](../../src/splatoon3_ai_coach/coach/score_facts.py).

ScoreFacts treats a `not_shown` penalty as zero **only for derived arithmetic**, carrying `penalty_not_shown_treated_as_zero` and an evidence limitation. It does not change the persisted penalty observation into an observed zero.

### 2.7 Tower Control — X active messages/pods; G checkpoint and movement experiments

The opt-in TowerControlDetector currently calls score-pod reading, explicit control-message matching, checkpoint-passed matching and checkpoint-at matching. It **does not call its `_marker` helper**. Raw results can therefore carry checkpoint cue scores without a marker location or checkpoint number.

Active `fuse_tower_observation` keeps fresh usable score pods with native values, boxes, hue and digit scores; it deliberately returns no marker and unknown marker/team presentation. The scan assigns `tower_team=None`; `resolve_tower_team` is not called there. Tower pods are not converted into team-specific remaining counts or progress.

`TowerControlMessageFuser` separately persists ally/opponent control or returning state from explicit messages, with establishing frame/result and grouped cue evidence where applicable. No current cue means hold the established state; ambiguous/mismatched cues can reset it. These state latches have no elapsed-time expiry. Unknown-start clips remain unknown until supporting evidence.

`ScenarioContext.objective` for Tower exposes only anchor/pre-death/lookback control samples with sample time, establishing time, observed/held quality and original evidence. It excludes raw pods/checkpoint experiments and sets progress null. Normal coaching and the public report do not consume this Tower payload.

The checkpoint fuser is not instantiated by active `fuse_game_state`; marker comparisons require populated marker snapshots that new active fusion does not produce. Ring measurement requires an externally supplied candidate center/hue and does not detect a ring's existence. Current production cannot claim Tower movement, checkpoint number/duration/clear, or player participation from these helpers. ### 2.8 Rainmaker — X independent count, possession and checkpoint streams

RainmakerScoreDetector reads native score pods with digit scores, geometry, hue and usability. Scan-time team association requires existing Ready-gated color calibration; unique hue matching assigns pod indices to teams and retains calibration provenance. Fusion accepts exactly one fresh timestamp-matched result in in-match Rainmaker with the map hidden. Without valid association it can preserve the raw score reading/IDs but leaves team counts null. It does not hold or interpolate counts.

Possession detector templates identify ally/opponent acquisition, loss and reset. Grouped observations retain first/last readable times, per-frame cues, language/template information and source references. The fuser establishes/holds ally possession, opponent possession or neutral; a directly observed opening-countdown→in-match transition may initialize neutral. A mid-match clip is not assumed neutral. Missing messages do not expire held possession automatically.

Checkpoint detector templates observe a per-team breakthrough message. The checkpoint fuser latches each team's first supported cleared fact with direct grouped evidence; all unestablished sides remain unknown, not uncleared. Count progress does not establish possession or a checkpoint clear.

`ScenarioContext.objective` receives three independent bounded sample sets and native-count progress observations. Count/possession/checkpoint provenance is retained, including held establishment time. Full message trajectories are in the manifest, not the three-sample context summary. The objective field is inspection-only, so these facts have no current gameplay coaching claim/report consumer. ### 2.9 Clam Blitz — X primary scores, penalties and basket appearance; G basket temporal facts

`clam_score` reuses deterministic primary/penalty digit reading under a distinct detector name. Fresh, visible in-match Clam results map fixed left/right HUD sides to ally/opponent primary counts and optional visible positive penalties. There is no score hold, no inference from an absent `+N`, and no basket dependency. Context inspection exposes sparse scores and per-team primary-count endpoint progress; increases/long gaps are unknown. These development readers do not establish how many clams a player carried or who scored.

ClamBasketStateDetector independently measures central HUD open/closed appearance and hue/concentration. Fusion preserves only fresh recognized visual state plus IDs under mode/phase/map gates; no hold or gameplay transition is invented. `resolve_basket_team` exists but `OPEN_STATE_VALIDATED=False` forces scoring-team attribution to unknown. The detector's 0.7 recognized-state signal is categorical, not an accuracy probability.

Basket state is **not** part of `ScenarioContext.objective` or another context field. `basket_open_runs.json` is built by an explicit diagnostic command, not normal analyze. Its frame/snapshot identity checks, scheduling provenance, unknown/missing-observation breaks, boundary samples and left/right censoring are already implemented. Separate temporal builders produce observed boundary spans, closing-time bounds and supplied-action-time relationships, retaining source-manifest identity and evidence IDs. A span between open observations is explicitly **not** continuous open duration. No existing builder joins score decreases to basket closure.

### 2.11 Timer, match identity, phase and acquisition metadata — P

TimerDetector emits an observed display and remaining seconds with a detector result. State fusion rejects temporally invalid increases, averages a five-value accepted window under the current defaults, and holds the last timer briefly; snapshot quality/last-observed time/age describe this timer path. Coaching GameClock instead takes usable integral **raw** timer readings, with timestamps, confidence and bounded lookup gaps, not the averaged/held snapshot value. The compact LLM view selects the death clock sample; other labeled samples remain in CoachInput. The report uses observed remaining-clock headings and explicit clock-aware durations.

MatchIntroDetector templates cover all five mode IDs and available stage labels in both language packs. The tracker latches stage/mode with template evidence into match identity; Ready? and team-color calibration are match side effects used to gate map sampling and supported team association. These identity/calibration records are not full per-observation context provenance today. Unknown identity stays unknown. The bounded game-language pre-scan selects detector templates independently of the coaching/report locale.

The early Review-icon tracker supplies acquisition metadata (and map-overlay observability), not a new gameplay event. Declared/review-detected video-source metadata and resolution are persisted with the manifest; they are distinct from actual objective/player observations. No detector chooses execution behavior from host/provider identity.

## 4. Temporal context: what can be reconstructed safely?

The default secondary window is `[scenario.start−8, scenario.end+2]` video seconds. It is not always a symmetric window around a death or a match-wide history. Anchor lookups normally have a 1-second bound; score pre-death target is death−0.5 and lookback is another 5 seconds earlier. These are configured video-time windows, not inferred gameplay time.

| Sequence question | Existing support | Limits / missing contract |
|---|---|---|
| Alive counts before/after a local death | Windowed compressed context trajectory; nearest anchor/death; separate labeled clock samples and offsets −5, −2, 0, +3, +6 seconds | Nearest lookup can choose a future observation; pre-death selector avoids it. Compression retains state onset but not last seen/gaps. Team counts do not identify participants or who died. |
| Objective progress before/after a team fight | SZ fresh primary-count observations with same-snapshot roster/lifecycle; RM/Clam equivalents in inspection-only objective context | There is no verified team-fight segmentation. ENGAGEMENT owns local splats only. Describe bounded observations around existing anchors, not “fight won/lost.” Three target samples omit many transitions. |
| Map coverage change before engagement | Sorted in-window map samples, each with percentages; full sidecar retains mask identity | Map opening is opportunistic and gated; unequal sampling geometry/calibration cannot be assumed comparable from the reduced context. No admitted delta/coverage sequence builder; one LLM ink sample can be post-death. |
| Special availability before a push | Windowed raw gauge readings and nearest-before/last-ready summaries | No “push” entity; no activation detector. Ready onset can mean first observed true, not exact charge time. No continuous ready duration through missing frames. |
| Consecutive local deaths and recovery | Death spacing, DEATH→RESPAWN→ACTIVE_AGAIN events, related engagement/death contexts, explicit incomplete/match-end closure | Event times are accepted observation times, affected by cadence/debounce. Plate end is not control return. Missing return evidence remains incomplete. |
| Clam scoring followed by basket closure | Fresh same-team primary-score observations; separate visual basket runs with explicit closing bounds | Not joined; basket scoring-team attribution unknown. Native count decrease is not scorer identity or a particular clam delivery. Must not compare unbounded times as continuous open duration. |
| Rainmaker acquisition → count change → checkpoint clear | Grouped direct messages, fresh counts and independent per-team clear evidence in manifest; bounded samples in objective context | No full ordered multi-stream context history/consumer yet. Held possession can outlive an undetected loss cue; never assume new state observations during hold. |
| Tower acquisition → progress → checkpoint | Acquisition/loss state is supported by direct messages | No active team-bound count progress or marker sequence; checkpoint message alone lacks number. “Returning” is a fused message state, not measured tower motion. |

### Timestamp, uncertainty and gap rules

- **Canonical identity/order:** video timestamps, event IDs, source frame IDs, optional PTS/time base; game-clock samples are separate raw usable TimerReadings. Held/smoothed `match_time_remaining` is never an observed coaching clock.
- **Sampling is not continuity:** at 2 FPS a frame-to-frame change only brackets what happened. Confirmation can delay acceptance. Raw detector timestamps may be echoes; special context correctly uses the enclosing frame timestamp. Grouped HUD-message first-readable time is not an exact gameplay transition time.
- **Quality labels are modality-specific:** snapshot `quality`, `last_observed_at` and `observation_age_seconds` are populated by timer fusion, not a unified confidence for every field. Event construction can use that snapshot quality to choose a coarse confidence; it is not a calibrated probability of the event. Roster, control and objective streams need their own provenance/quality interpretation.
- **Held state is not fresh evidence:** Tower/Rainmaker objective samples retain sample time and establishing time and distinguish observed versus held. Message fusers do not expire held states by elapsed time. Unknown/missed intermediate cues therefore remain a risk even when the latest sample is structurally supported.
- **Different lookup semantics coexist:** roster anchors use nearest absolute time; pre-death roster uses before-cutoff; score samples prefer both-observed within a backward window; legacy zone samples skip unknowns within a bound; the new objective sampler selects the latest snapshot and does not search backward past an unknown. A reusable envelope must expose the actual method rather than pretend all fields are simultaneous.
- **Unknowns may be skipped within bounded endpoint comparisons:** progress adapters compare fresh same-team endpoints within the maximum gap even if intermediate snapshots have no value. This supports endpoint arithmetic, not uninterrupted progress/stoppage. Splat Zones labels a count increase no_progress with a negative normalized amount; Rainmaker/Clam leave an increase unknown. That verified semantic asymmetry needs explicit validation before cross-mode reuse. Generic temporal facts return selected endpoint intervals/stop bounds, not continuous fight outcomes.
- **Clock conversion:** PlaybackClockInfo estimates a match-level rate from observed countdown slopes and records spread/counts/reason. ClockedDuration preserves raw video duration, selected clock/method, endpoint gaps and uncertainty. A match-level median is not a validated piecewise pause/cut/speed-change model. No fabricated `300−video_time` clock is permitted. [Playback implementation](../../src/splatoon3_ai_coach/coach/playback_clock.py), [raw clock](../../src/splatoon3_ai_coach/coach/game_clock.py).
- **Playback-sensitive roster validity:** roster plausibility minimums and grouping windows are configured in video seconds. The fixed conservative plausibility interval is not an independently established actual teammate respawn duration, particularly on variable-speed replays.
- **Match end:** samples at/after accepted MATCH_END are excluded from context/clock loading. Clock zero is supported; overtime/knockout normally have no MATCH_END, so the domain can remain the whole video. The HUD-loss fallback stays off. No FINISH detector confirms those boundaries. [Boundary](../../src/splatoon3_ai_coach/analysis/match_bounds.py), [decision](../../src/splatoon3_ai_coach/vision/match_end.py).
- **Review clocks stay separate:** glyph estimates, lamp-second observations and alignment intervals have their own uncertainties and provenance. Review `alive` means no X seen; disconnection can read alive. Missing glyphs never prove no death/use. Alignment structural pairing is not proof of match identity and has overtime/cut restrictions.

### Specific temporal risks to validate, not inferred gameplay facts

1. **Roster compression/freshness:** verified implementation drops repeated equal states before pre-death selection, and does not reset equality on missing snapshots. Hypothesis: after a visibility gap it can make a late pre-death selection look more continuously supported than its retained first point establishes. Test an unchanged state, a long hidden interval and an unchanged return before deciding any repair.
2. **Held possession/control:** verified fusers retain last supported state without time expiry. Hypothesis: missed loss messages can produce stale held state at an anchor. A useful improvement would expose age/coverage; a timeout policy would be a separate semantics change requiring evidence.
3. **Mode provenance:** verified context construction uses the identity sidecar while fusion/coaching can replay intro readings. Hypothesis: an older missing identity sidecar can explain absent context despite preserved objective snapshots. Characterize stored artifacts before adding any fallback.
4. **Whole-match speed estimates:** variable speed/cuts can preserve a reasonable median rate but invalidate a local duration. No dataset-specific prevalence was measured here; test piecewise timing before proposing local conversion.

### Recommended first implementation slice: preserve existing roster and map-ink evidence

**Scope for a later authorized change:** enrich the existing sparse `players` and `map.ink` projections with backward-compatible source references/quality and observation-coverage information. Do not change counts, ink classification, thresholds, fusion, scenario ownership, selection, ranking, claims or prompts.

1. Design a small reusable observation-reference model: source/result IDs, observed video time, optional frame/PTS reference, source-specific quality/availability and artifact identity. Retain raw fields in source artifacts; do not copy arbitrary English narration into evidence.
2. For roster, retain original source/confidence and record explicit visibility/observation breaks before compression. Preserve both the retained state-start and last actual confirming observation, or another reviewed bounded representation. A known equal value after a hidden interval must not silently certify continuity. Choose the representation from fixtures before changing a lookup policy.
3. For map ink, retain stage/mode, sample-mask source and polygon hash, raw denominator/pixel totals and source overlay references. Link calibration identity when available; legacy missing links stay unavailable. Keep share-of-detected-ink separate from visible-ink fraction.
4. Serialize and round-trip the enriched context while preserving existing leaves and derived claims byte-for-byte where possible. Default LLM/report projections should initially ignore the added metadata, as the objective inspection field already does for an intentional migration boundary.

**Acceptance checks:** unchanged source values and event/scenario identities; retained references resolve to stored artifacts; no inferred continuity across gaps; missing metadata is explicit; no samples at/after MATCH_END; context JSON round trips; old artifacts load; default CoachInput/LLM claims and ranking are unchanged; geometry/calibration mismatch cannot support a map delta. Include default-enabled common paths across all five modes, and capability-off paths. This slice does not require a new detector or subjective human rating task.

A later slice can expose existing Clam basket bounds and native objective observations through the same structure. It must keep basket team unknown until the separate validation block is resolved.
